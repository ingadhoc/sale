==========================
Sale Order Type Automation
==========================

#. Add to sale order type this options to be executed automatically on sale order confirmation and picking confimation:

    * Create / Validate Invoice
      * New domain to filter invoices for automatic validation. So, if this filter does NOT find the invoices, they stay in drafts status.
    * Create / Validate Payment
    * Confirm picking and products transfer (only on sale order confirmation)


Integration with Account Background Post
========================================

When ``account_background_post`` is installed (optional), the invoice validation can be deferred
instead of blocking the operation:

1. **Error traceability.** When the background post cron cannot validate an invoice generated by
   this automation, the error is logged on the source sale order chatter (the order is resolved
   through the invoice lines), notifying its internal followers. The invoice keeps a pointer to
   that order, so a draft invoice always says where its error is.

2. **The order is not confirmed if the invoice fails.** The whole confirmation is aborted, so
   nothing is left half done: no confirmed order hiding the failure and no invoice left as posted
   without number nor document type. The user gets a *Confirm anyway* call to action that confirms
   the order leaving the invoice marked to be validated by the background post cron.

   The error is logged on the order through a separate database connection, so the trace survives
   the rollback. Being a separate connection, it only sees what is already committed: an order
   created in the very same transaction that confirms it (an API call doing both at once) is not
   there yet, so that error travels only in the message the user gets.

   Aborting is the behaviour up to v18. The flows that cannot be torn down (the batch run, which
   already committed) or that deferred the validation on purpose (API, background post) keep logging
   the error and confirming the order.

3. **A deferred invoice always says so.** Whenever an invoice is left in draft to be validated in
   background, both the order and the invoice get a note with the reason, and the invoice points to
   the order, where the error is. A draft invoice is never a mystery.

4. **Transfers.** The same call to action (*Validate anyway*) is offered when the invoice automation
   triggered by a transfer validation fails. When validating more transfers than the background post
   batch size (system parameter ``account_background_post.batch_size``, 20 by default), the invoices
   are directly created to be validated in background, so a big batch is never blocked by the
   invoice validation. That decision is not asked but it is never silent: the user also gets a
   notification when the transfers are validated.

Without ``account_background_post`` there is nothing to defer to, so there is no call to action:
the confirmation is still aborted and the user gets the plain error, exactly as in v18.
